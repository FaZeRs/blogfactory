## Task A: learned style rules

A owns `services/learning/`, `routes/learning.ts`, the prompt files and the prompt-variable code in the engine stages and localization, and the Brand Voice page.

1. **Migration 0046:** add `learning_signals` and `style_rules` as in the spec, with indexes on `(user_id, site_id, created_at)` and `(user_id, site_id, status)`. Mirror them in `schema.ts`.
2. **Signal capture** (`services/learning/signals.ts`):
   - **`recordEditSignal`** runs when a person saves:
     - an engine-made post (a post that has an `article_runs` row whose `post_id` is it): hook into the post update path, `updatePostWithRevision` with source `save`, or the route; keep it best-effort and never failing the save;
     - a translation, through the PUT route in `routes/post-translations.ts`.
   - **What it stores:** a word-level diff between the engine's text and the person's.
     - For a post, the engine's text is revision 1's content; for a translation, the last engine-written text, so store `engine_content` on the row when the engine writes it, or diff against the previous version. Choose the simplest correct option and explain it.
     - Use a simple LCS on words, or an installed diff library if one exists (check `package.json` files first).
     - Keep at most 40 changed hunks, each shortened to 160 characters, plus an `editRatio`.
   - **Upsert:** one row per post, locale and day.
   - **`recordCommentSignal`** runs from `services/post-revise-comments.ts` (posts) and the translation `/revise` route.
3. **Distill** (`services/learning/distill.ts`) plus `prompts/learning-distill.md`:
   - per the spec, with a weekly worker task (per enabled site, Sunday UTC) and `POST /api/learning/distill?siteId` started detached, returning 202;

4. **Eval check** (`services/learning/eval-check.ts`): `POST /api/learning/rules/:id/eval` is detached. It reuses `server/src/engine/evals/run.ts` (`runEval` / `generateEngineArticle`) with the first 3 golden briefs. Inject the candidate rule through the same style-rules variable, using the site's models via `userEngineLlm`, and store the summary on `style_rules.eval`. If the harness can't take rules, add a minimal option.
5. **Routes** (`routes/learning.ts`, mounted at `/api/learning`):

   - `POST /rules/:id/approve`, with an optional `{rule}` for edit-and-approve; it applies a retire op by retiring its target;
   - `POST /rules/:id/reject`, `POST /rules/:id/retire`;
   - `POST /distill`, `POST /rules/:id/eval`;
   - `GET`/`PUT /settings`.
   - Every route is scoped by user and site. Include a self-test.
6. **Injection:** a `styleRulesText(userId, siteId, scope)` helper. Wire it into the brief, draft, revise, revise-comments, localize and localize-review prompts as a fenced block, with the Lindevo guard sentence, per the spec. Bump every prompt version you change. ## Task B: refresh queue

B owns `services/refresh/`, the Ideas changes, `engine/article-runs.ts`, the `deliver` stage and the Ideas UI. Don't edit the prompts.

1. **Migration 0047:** add `ideas.refresh_post_id uuid null` (references `posts` on delete set null) and `ideas.refresh_reason text null`, with an index on `(user_id, site_id, refresh_post_id)`. Mirror them in `schema.ts`.
2. **Detection** (`services/refresh/detect.ts`), per the spec, reusing `services/optimize.ts` and `services/search-console.ts` data. The thresholds:
   - age ≥ 90 days from the first CMS publication (`post_publications`);
   - clicks −30% (28 days against the previous 28, ending 3 days ago), with previous clicks ≥ 10, **or** position worse by ≥ 5;
   - **or** striking distance: position 8–20 with ≥ 100 impressions;
   - no open refresh idea or run, a 28-day cooldown, and at most 2 new candidates per site per day.

   It creates Ideas rows with `origin: "refresh"`, a title such as "Refresh: <post title>", the reason, and a short brief. Follow how manual or discovered ideas are inserted; scores can be simple, since the reason matters more. Add a daily worker task and pure-function tests for the thresholds.
3. **Approve and schedule:** a refresh idea, when started, calls `startArticleRun` with `settings.refreshPostId`, `guidance.angle` set to the spec's sentence, and `guidance.instructions` set to "Searches this post already appears for:" plus the top 10 Search Console queries of the last 28 days. Its topic is the post's title or primary keyword. Find where ideas start runs (`services/ideas/schedule.ts` `startDueIdeas` / `bookIdea`, and the run start) and add the minimal branch.
4. **Deliver:** when `run.settings.refreshPostId` is set and the post belongs to the user and site:
   - write a new revision with `updatePostWithRevision` (source `refresh`; add it to the allowed sources if they are an enum) instead of creating a post;
   - set the editorial state back to `in_review`;
   - link the run's `post_id` to the existing post;
   - keep the publication rows;
   - the translations go stale through the existing stale rule.

   Note the "edited while refreshing" case per the spec. Include engine tests with the fake LLM: deliver updates the same post, creates no new post, adds the revision, and leaves the translation stale.
5. **Web:** the Ideas Inbox and cards show a **Refresh** badge, the reason, and a link to the post (`web/src/components/ideas/IdeaCard.tsx`). Add a vitest.
